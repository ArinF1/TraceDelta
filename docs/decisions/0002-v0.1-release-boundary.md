# ADR 0002: Finite v0.1 release boundary

## Status

Accepted

## Context

The original roadmap described a broad progression from parser compatibility through semantic analysis and future source attribution. That direction was useful during project formation, but it did not define a finite point at which TraceDelta could honestly publish v0.1. Continuing to add semantic rules or exporter variants before shipping the basic workflow would turn v0.1 into an open-ended program.

The first release needs to prove one product claim: a developer can supply realistic OpenTelemetry OTLP JSON from a known-good run and a proposed run, receive a deterministic and privacy-conscious regression report locally or in a pull request, and install a versioned binary to repeat that workflow.

## Decision

TraceDelta v0.1 is limited to the following release contract:

1. Read either one OTLP/HTTP JSON `ExportTraceServiceRequest` object or a trace-only OTLP File Exporter JSON Lines stream of `TracesData` objects. The documented profile covers multiple resource/scope groups and traces, standard numeric enums and 64-bit JSON encodings, primitive and nested `AnyValue` values, and safe acceptance of span events and links. It is not a promise to accept vendor envelopes or unrelated telemetry types.
2. Normalize generated identifiers, absolute clocks, ordering, and configured duration noise, then match traces and spans deterministically. Unresolved ambiguity is reported; raw IDs are never used as cross-run identity.
3. Detect only the v0.1 regression set: added spans, removed spans, error-state changes derived from span status plus the safe `error.type` attribute, and latency increases that meet both configurable relative and absolute thresholds (defaults: `20%` and `10ms`). Error messages and exception stack traces are not evidence.
4. Produce equivalent, deterministically ordered terminal, versioned JSON, and self-contained offline HTML reports from one comparison result.
5. Redact common credential and personal-data attribute keys before matching evidence or findings are constructed, allow users to add denylisted keys, and render only an explicit safe evidence set. Redaction reduces accidental disclosure but is not presented as anonymization.
6. Ship a reusable GitHub Action that compares user-supplied artifacts with least-privilege defaults and preserves the distinction between a regression (exit `1`) and a tool/input failure (exit `2`). Trace collection remains the caller's responsibility.
7. Include a small example application and a deliberately regressed public pull request that demonstrate the Action and all v0.1 finding categories with synthetic telemetry.
8. Gate the release with unit and integration tests, race-enabled tests, and focused fuzz targets for untrusted parsing, matching determinism, and reporter escaping where they add distinct value.
9. Publish tagged, versioned binaries for Linux amd64/arm64, macOS amd64/arm64, and Windows amd64 with SHA-256 checksums, plus a reproducible 45–60 second demonstration linked from the README.

The v0.1 command remains a local, in-memory comparator. It does not collect telemetry or execute the applications under comparison.

The following are explicitly outside v0.1: database statement-shape analysis, general service-call or relationship-change rules, metrics or log comparison, hosted storage or dashboards, pull-request commenting APIs, source attribution, plugin/rule runtimes, statistical aggregation across repeated runs, exhaustive OTLP/vendor compatibility, and automated application execution.

## Consequences

Positive consequences:

- The release has a finite checklist tied directly to a demonstrable pull-request workflow.
- The semantic surface is small enough to make deterministic matching, redaction, and cross-format consistency credible.
- A versioned binary and reusable Action make the work consumable without operating a hosted service.
- Deferred analysis features can be evaluated against actual v0.1 usage instead of delaying the first release.

Costs and limitations:

- v0.1 will intentionally miss behavioral changes outside added/removed spans, errors, and latency.
- Some valid OTLP JSON producer/file shapes will remain unsupported and must fail with actionable diagnostics.
- Key-based redaction and safe evidence selection cannot prove that arbitrary telemetry is anonymous.
- Users must arrange representative baseline and candidate trace collection themselves.

## Alternatives considered

- **Keep every existing semantic rule in v0.1:** Rejected because database shapes, relationship analysis, and broad service semantics multiply matching and privacy requirements without being necessary to demonstrate the core product.
- **Call the current vertical slice v0.1:** Rejected because text-only output, percentage-only latency, no early redaction, and no installable CI path are not a credible reusable release.
- **Delay packaging and demonstration until after v0.1:** Rejected because installability and a reproducible end-to-end example are part of proving that the comparator works as a product rather than only as a library prototype.
- **Promise complete OTLP JSON compatibility:** Rejected because vendor envelopes and exporter behavior vary; the official OTLP/HTTP JSON and trace-only OTLP File Exporter shapes form a useful tested profile without claiming universal compatibility.
